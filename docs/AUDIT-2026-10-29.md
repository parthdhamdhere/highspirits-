# Website audit and regression verification

Date: 29 October 2026. Scope: the current local Next.js frontend, Fastify API, shared contracts, SQL schema and background jobs. Existing uncommitted work was preserved. These changes have not been deployed.

## Outcome

Fixed the reproducible defects listed below and added repeatable tests. A fresh account could log out in the initial ordinary-browser reproduction. A changed session in another tab leaves the original client with a stale CSRF token; previously that rejection stopped logout without visible feedback. Recovery from that condition is now tested through the real browser. Account deletion followed by logout is also tested.

This is a substantial local audit, not a certification that every possible bug or vulnerability is absent.

## Fixes

| Priority | Defect | Result |
| --- | --- | --- |
| P1 | Session changes could reject logout with an unhandled error | A CSRF rejection refreshes the session token and retries once. Other errors are never automatically replayed. Customer and staff logout show errors and busy states; successful logout clears the client view and opens login with a full navigation. |
| P1 | Authentication retained the previous session and used a different anonymous CSRF cookie | Login invalidates the session it replaces and synchronizes the CSRF cookie. Revoked session replay is rejected. |
| P1 | A suspended staff invitation could reactivate its account | Acceptance requires an invited account. Suspension revokes invitation tokens and sessions. |
| P1 | Configured staff authenticator secrets were ignored | Accounts with a TOTP secret must supply a valid code; management login accepts that code. |
| P1 | Deletion retained birth date and password hash | Deletion clears both, along with contact details, names, sessions, tokens and queued emails. Migration also clears credentials and birth dates from previously deleted accounts. |
| P1 | A payment arriving after deletion could issue tickets again | Capture locks the account before the booking, detects deletion and queues reversal without issuing tickets or email. |
| P1 | Checkout could proceed after an event was cancelled; past events appeared on sale | Checkout, capture and public availability now check event state/time. Manual bookings reject unavailable events. Event edits and booking transactions share an event lock. |
| P1 | Expired payments could bypass the four-booking account cap | Reacquisition checks the cumulative limit before taking inventory again. |
| P1 | Female/couple tiers accepted inconsistent guest counts | Shared validation requires one guest for female tickets and two for couple tickets. |
| P1 | Password authentication bypassed the configured bot check | Both password login and registration invoke it; customer and staff forms render the configured challenge. Verification requests have a timeout. |
| P1 | Missed webhooks and ambiguous provider orders had no automatic reconciliation | The worker checks up to ten eligible orders per run, recovers an existing provider order by exact receipt/amount/currency and processes captured payments idempotently. It never creates a second order during recovery. Failures are recorded for review. |
| P1 | Production configuration accepted an empty webhook secret or missing bot site key | Startup validation rejects both. Existing HTTPS, PostgreSQL, payment, email and no-demo requirements remain. |
| P2 | Editing an event with a manual reservation attempted to delete referenced tiers | Manual reservations lock tier structure just as customer holds do; event details remain editable. |
| P2 | Updating an invited employee's role could prevent invitation acceptance | Invited status and its link survive a role-only edit. Missing staff updates return 404. |
| P2 | Manual reservations accepted invalid phone numbers and could miss released inventory | They use the shared phone validator and expire old holds before checking inventory. |
| P2 | Profile failures could leave an endless loading indicator | The failure is announced and loading ends. |
| P2 | Login headings wrapped poorly at tablet/small-phone widths and footer text was undersized | Layout/type adjustments and a 12px footer improve readability while retaining the approved brand. |

## Remaining release verification and limitations

1. **Live integrations:** no real Razorpay charge/refund, Resend delivery or live Turnstile challenge was executed. Reconciliation and email retries have simulated-provider tests. Staging must verify signatures, retries, provider timeouts, refund settlement and delivery. Provider-contract references: [Razorpay order/payment API](https://github.com/razorpay/razorpay-node/blob/master/documents/order.md), [order receipt lookup](https://github.com/razorpay/markdown-docs/blob/master/api/orders/fetch-all.md).
2. **Production database and load:** actual PostgreSQL transaction races, multiple workers, connection pool saturation and the specified 20,000-user spike were not tested. The bounded reconciliation batch also needs production backlog/throughput verification.
3. **Operational handling:** reconciliation errors are stored in `orders.reconciliation_error`; exhausted email/refund retries remain available in the database. Alerting, operational review, backup/restore and infrastructure behavior require deployment setup and verification.
4. **Staff MFA lifecycle:** existing TOTP secrets are enforced, but enrollment/recovery and mandatory MFA provisioning are not provided by the current website. Those need a defined operational flow before claiming complete staff MFA support.
5. **Browser/accessibility scope:** Chrome emulation and keyboard checks passed. Safari, Firefox, physical mobile touch, assistive technologies and a complete WCAG evaluation were not run. No WCAG certification is asserted.
6. **Business configuration:** actual GST treatment, final policies and live credentials still need venue confirmation. Production checkout remains gated on tax confirmation.
7. **Security scope:** no independent penetration test or deployment-level audit was performed. The frontend has no strict nonce-based content-security policy; that is a defense-in-depth follow-up requiring staging validation with the payment and challenge scripts.
